# Mova UI-kit

Рабочий локальный MVP мессенджера Mova в тёмном стиле Liquid Glass.

Реализованы регистрация и вход, личные и групповые чаты, постоянное хранение сообщений, синхронизация через WebSocket, голосовые сообщения с waveform/перемоткой/скоростью воспроизведения и звонки через WebRTC.

## Запуск

Требуются Node.js 22.5 или новее и pnpm.

```bash
pnpm install
pnpm dev
```

Одна команда запускает frontend и локальный API. Приложение откроется на `http://127.0.0.1:5173`, API — на `http://127.0.0.1:8787`.

### Запуск двойным кликом на macOS

В папке `click` лежат готовые команды Finder:

- `Start.command` — запускает Mova в фоне и открывает сайт;
- `Test-Call.command` — запускает Mova и открывает две независимые вкладки для проверки звонка;
- `Test.command` — запускает тесты, production-сборку и интеграционную проверку;
- `Status.command` — показывает состояние web/API и последние строки лога;
- `Restart.command` и `Stop.command` — перезапускают и останавливают локальную Mova;
- `Deploy.command` — после подтверждения прогоняет проверки, создаёт коммит и отправляет его в GitHub.

Логи локального запуска сохраняются в `.mova-runtime/dev.log`, результаты последней проверки — в `.mova-runtime/last-test.log`.

Данные сохраняются локально в SQLite `.mova-data/db.sqlite`, а вложения — в `.mova-data/uploads`; оба пути не попадают в Git. При первом запуске существующий `.mova-data/db.json` автоматически импортируется, включая вложения и отметки о прочтении. Исходный JSON остаётся нетронутым как резервная копия.

SQLite работает в WAL-режиме с индексами по чатам, участникам и времени сообщений. Фотографии перед отправкой обрабатываются на устройстве пользователя: небольшие файлы сохраняются без изменений, крупные уменьшаются максимум до 4096 px и кодируются в WebP с качеством 93%. Перекодированный вариант используется только при заметном уменьшении размера. Сервер получает готовый бинарный файл, поэтому изображения не раздувают базу как base64 и не расходуют серверный CPU на обработку.

История сообщений загружается страницами по 80 записей через стабильный курсор `(createdAt, id)`. При прокрутке вверх более ранняя страница добавляется без скачка позиции, а после восстановления WebSocket активный чат автоматически сверяется с сервером.

### Локальный cache и offline-очередь

Списки чатов, пользователей, уже загруженные страницы сообщений и незавершённые отправки сохраняются в IndexedDB отдельно для каждого аккаунта. После перезапуска Mova сначала показывает локальные данные, затем обязательно сверяет их с сервером.

Сообщение, созданное без соединения, сразу получает состояние «В очереди». Текст, reply-контекст и вложение сохраняются вместе с неизменяемым `clientId`. После события `online` или восстановления WebSocket очередь отправляется по порядку. Если файл успел загрузиться до обрыва, повтор использует уже полученный URL; серверный уникальный индекс на `(authorId, clientId)` защищает от дублей при потерянном HTTP-ответе. При явном выходе из аккаунта его локальный cache и outbox удаляются с устройства.

### Резервные копии

Сервер раз в сутки создаёт атомарный snapshot SQLite вместе со всеми зарегистрированными вложениями. По умолчанию сохраняются 14 последних копий в `.mova-data/backups` локально или `/data/backups` в Amvera. Каждый backup содержит manifest с SHA-256 и проходит `PRAGMA integrity_check` до публикации.

```bash
pnpm backup create
pnpm backup list
pnpm backup verify /полный/путь/к/backup
pnpm backup restore /полный/путь/к/backup /новая/пустая/папка
```

Восстановление намеренно разрешено только в новую пустую папку: остановите сервер, проверьте восстановленную копию и затем отдельно замените рабочие данные. Настройки: `MOVA_BACKUPS_ENABLED=false` отключает расписание, `MOVA_BACKUP_PATH` меняет каталог, `MOVA_BACKUP_INTERVAL_MS` — интервал (минимум минута), `MOVA_BACKUP_RETENTION` — число копий.

Для проверки общения между двумя пользователями откройте Mova в двух вкладках и зарегистрируйте разные аккаунты: сессии хранятся отдельно для каждой вкладки.

### Почта и восстановление доступа

Новая регистрация завершается только после ввода шестизначного кода из письма. Такие же одноразовые коды используются для восстановления пароля и подтверждения нового адреса в разделе «Настройки → Аккаунт». Код действует 10 минут и блокируется после пяти неверных попыток; после сброса пароля или смены почты старые сессии отзываются.

Для отправки писем настройте SMTP одним URL:

```bash
MOVA_SMTP_URL="smtps://user:password@smtp.example.com:465"
MOVA_EMAIL_FROM="Mova <no-reply@hola-mova.ru>"
```

Или отдельными переменными `MOVA_SMTP_HOST`, `MOVA_SMTP_PORT` (обычно `587`), `MOVA_SMTP_SECURE` (`true` для implicit TLS), `MOVA_SMTP_USER`, `MOVA_SMTP_PASSWORD` и `MOVA_EMAIL_FROM`. Без SMTP сервер продолжит обслуживать существующие аккаунты, но запрос нового кода вернёт понятную ошибку. Для локальной разработки можно явно включить `MOVA_EMAIL_MODE=console`: коды будут напечатаны в терминале, поэтому этот режим нельзя использовать в production.

Во время первого голосового звонка браузер запросит доступ к микрофону. Для связи за пределами локальной сети потребуется HTTPS и production TURN-сервер.

## Desktop-приложение

Mova можно запускать как нативное окно Electron. В режиме разработки desktop-клиент сам запускает локальные web и API:

```bash
pnpm desktop:dev
```

Сборка установщиков:

```bash
pnpm desktop:build:mac
pnpm desktop:build:win
pnpm desktop:build:linux
```

Артефакты появляются в `release/`. При первом запуске production-сборка попросит указать публичный HTTPS-адрес Mova на Amvera; изменить его позднее можно через меню приложения. Desktop-клиент разрешает микрофон, уведомления и системный выбор окна для демонстрации экрана только для настроенного origin.

Проверка обновлений настроена через GitHub Releases. Для публичного распространения macOS-сборку нужно подписать сертификатом Developer ID и notarize, а Windows-сборку — подписать code-signing сертификатом.

## Публикация на Amvera

В репозитории уже находятся `Dockerfile` и `amvera.yaml`. При запуске в Amvera
приложение использует публичный порт `80`, база сохраняется в `/data/db.sqlite`,
а вложения — в `/data/uploads`. Старый `/data/db.json`, если он существует,
будет автоматически импортирован и сохранён как резервная копия.

1. Создайте в Amvera новое приложение и загрузите в него этот Git-репозиторий.
2. В разделе «Переменные» добавьте **секрет** `MOVA_SESSION_SECRET` со случайным
   длинным значением (не менее 32 символов).
3. Добавьте SMTP-настройки из раздела «Почта и восстановление доступа». Логин и пароль SMTP храните как runtime-секреты.
4. Для стабильных звонков добавьте данные внешнего TURN-сервера как runtime-секреты:
   `MOVA_TURN_URLS` (несколько адресов разделяются запятыми, желательно UDP/TCP и
   TLS на 443), `MOVA_TURN_USERNAME` и `MOVA_TURN_CREDENTIAL`. Сам TURN нужно
   разместить у провайдера с публичными UDP-портами: HTTP/HTTPS-прокси Amvera
   медиатрафик TURN не заменяет. Вместо трёх переменных можно задать
   `MOVA_ICE_SERVERS` — JSON-массив в формате `RTCIceServer[]`.
5. Запустите сборку, затем приложение. После изменения переменных перезапустите контейнер.
6. В настройках сети добавьте бесплатный домен Amvera с типом подключения HTTPS
   и портом `80`.
7. Проверьте `https://<ваш-домен>/api/health` и `https://<ваш-домен>/api/ready`, затем откройте сам домен. Prometheus-метрики доступны по `/metrics`. В production задайте `MOVA_METRICS_TOKEN`: после этого scraper должен передавать `Authorization: Bearer <token>`.

Сервер пишет однострочные JSON-логи с `instanceId`, событием и безопасными полями. Каждый HTTP-ответ содержит `x-request-id`; входящий корректный `x-request-id` сохраняется, поэтому запрос можно связать между reverse proxy и Mova. Метрики включают histogram задержки по нормализованным маршрутам, статусы HTTP, типы WebSocket-событий, rate-limit/rejection, активные звонки, участников voice room, event-loop delay, состояние backup и размеры основных таблиц.

Готовые правила для Prometheus/Alertmanager находятся в `ops/prometheus-alerts.yml`: HTTP 5xx, p95 latency, блокировка event loop, ошибки/устаревание backup и всплеск WebSocket rejection. Перед production-включением укажите актуальный receiver и маршрутизацию уведомлений в своей конфигурации Alertmanager.

### Production-мониторинг в Grafana

Основная панель владельца и агентов: [Mova — состояние сервиса](https://chipperpoppy1894.grafana.net/d/mova-production/mova-e28094-sostojanie-servisa). Grafana выполняет внешний запрос к `https://hola-mova.ru/api/ready` из Stockholm каждые 5 минут и продолжает мониторинг независимо от открытой вкладки или запущенного агента.

Быстрая интерпретация панели:

- «Работает», HTTP `200`, ошибки `0%` — сервис отвечает нормально;
- рост задержки или ошибки доступности — сопоставьте время с deployment и серверными логами;
- `resolve`, `connect`, `tls`, `processing`, `transfer` показывают, на каком этапе запроса появилась задержка;
- срок TLS-сертификата позволяет заранее заметить проблему с HTTPS.

Правила `Failed Checks [5m]` и `TLS Certificate` находятся в Grafana Alerting. Без настроенного contact point тревоги видны в Grafana, но не отправляются по email. Панель использует постоянный бесплатный лимит Synthetic Monitoring; не переводите аккаунт на платный план для этой конфигурации.

Воспроизводимая конфигурация хранится в `ops/grafana-dashboard.json`, а расширенные Prometheus-правила — в `ops/prometheus-alerts.yml`. Мониторинг не получает переписку, аудио или видео пользователей.

Во время звонка кнопка копирования рядом с индикатором сети формирует локальный JSON-отчёт для поддержки. В него входят RTT, jitter, packet loss, interval bitrate аудио/видео, codec, FPS, encoded/decoded/dropped frames, freezes и факт TURN-маршрута. Отчёт намеренно не содержит ID чата и пользователей, IP/ICE-адресов, названий устройств или содержимого медиа.

Для локальной проверки production-режима:

```bash
pnpm build
MOVA_SESSION_SECRET=local-production-check pnpm start
```

### Banner во время deployment

Maintenance-состояние хранится на persistent volume рядом с SQLite (`/data/maintenance.json` в Amvera). На backend задайте отдельный длинный секрет `MOVA_DEPLOY_HOOK_SECRET`. Deployment process должен использовать тот же секрет и публичный URL:

```bash
export MOVA_DEPLOY_URL="https://<ваш-домен>"
export MOVA_DEPLOY_HOOK_SECRET="<секрет из backend environment>"
MOVA_DEPLOYMENT_ID="deploy-$(date -u +%Y%m%dT%H%M%SZ)"

pnpm maintenance on "$MOVA_DEPLOYMENT_ID"
# Здесь выполняется фактический deploy новой версии.
pnpm maintenance wait-ready "$MOVA_DEPLOYMENT_ID" 900
```

`wait-ready` ждёт успешный `/api/ready` от нового `instanceId` и только после этого выключает banner. При ошибке или timeout команда завершается с кодом 1, а maintenance остаётся включённым. Для ручного снятия после проверки: `pnpm maintenance off "$MOVA_DEPLOYMENT_ID"`.

`scripts/deploy.sh` выполняет всю последовательность автоматически одной командой. По умолчанию он использует `https://hola-mova.ru` и получает secret из `MOVA_DEPLOY_HOOK_SECRET` или macOS Keychain (`service: mova-deploy-hook`). Secret в файлах проекта не хранится. Если предыдущий deploy завершился ошибкой, повторный запуск продолжает оставшийся активным maintenance вместо требования ручного `off`. Первый rollout поддержки maintenance выполняется обычным способом, потому что старая версия backend ещё не содержит hook endpoint.
