# Технический аудит и дорожная карта Mova

Дата аудита: 11 августа 2026 года.

Этот документ описывает текущее состояние репозитория, а не желаемую архитектуру «с нуля». Выводы сделаны по `README.md`, `AGENTS.md`, `package.json`, коду в `src/`, `server/`, `desktop/`, `public/` и по всем проверочным пунктам переданного MD-файла. Отдельного второго файла со списком багов в задаче не было, поэтому раздел «Разбор MD» ниже охватывает все конкретные пункты из полученного файла.

На этом проходе поведение Mova не менялось.

## Короткое резюме

Mova уже не является пустым UI-макетом. В ней есть настоящий сервер, постоянная SQLite-база, бинарные вложения, WebSocket-события, быстрый локальный показ отправляемого сообщения, статусы отправки и прочтения, WebRTC-звонки, базовая диагностика качества связи и защищённая Electron-оболочка.

Главный разрыв между текущей Mova и ощущением надёжности Telegram находится не в дизайне. Сейчас клиент умеет сразу показать сообщение, но не умеет гарантировать, что повтор запроса после обрыва сети не создаст копию. После переподключения WebSocket список чатов обновляется, а открытая история — нет. Неотправленное сообщение и cache также пропадут после перезапуска страницы или приложения.

Поэтому первый приоритет — сделать отправку повторяемой без дублей и дать пользователю безопасную кнопку «Повторить». После этого нужно закрыть пропуски истории при reconnect, добавить пагинацию и только затем строить постоянный локальный cache/offline-очередь.

## 1. Как Mova устроена сейчас

### Карта основных частей

| Область | Где находится | Что делает |
| --- | --- | --- |
| Запуск React | `src/main.tsx` | Показывает лендинг на `/` и реальное приложение на `/app`. |
| Основной интерфейс | `src/RealApp.tsx` | Авторизация, список чатов, история, composer, optimistic-сообщения, уведомления и большая часть UI звонка. |
| HTTP и WebSocket-клиент | `src/lib/api.ts` | API-запросы, загрузка вложений, сессия, heartbeat и reconnect WebSocket. |
| Звонки | `src/hooks/useVoiceCall.ts` | Микрофон/камера/экран, WebRTC peers, сигналинг, ICE restart и WebRTC stats. |
| Уведомления | `src/lib/messageNotifications.ts` | Web Notification для нового сообщения, когда окно неактивно. |
| Подготовка изображений | `src/lib/imageCompression.ts` | Уменьшает крупные изображения и при выгоде переводит их в WebP. |
| HTTP/WebSocket-сервер | `server/index.mjs` | Авторизация, API, broadcast событий, сигналинг звонков, раздача frontend и файлов. |
| Постоянные данные | `server/database.mjs` | SQLite-схема, транзакции, сообщения, чаты, прочтения, файлы и миграция старого JSON. |
| Desktop | `desktop/main.mjs` | Electron-окно, доверенный сервер, разрешения ОС, выбор экрана и автообновление. |
| Первичная настройка desktop | `desktop/setup.html`, `desktop/setup-preload.cjs` | Безопасно сохраняет HTTPS-адрес сервера Mova. |
| Статические ресурсы | `public/` | Иконки, логотип, manifest, robots и sitemap. |

`src/App.tsx`, `src/components/Product.tsx` и `src/data.ts` относятся к UI-kit/Storybook-демо. Реальный пользовательский путь запускается через `RealApp`, поэтому новую логику сообщений нельзя случайно внедрять только в демонстрационный `App`.

### Что происходит при запуске

1. `src/main.tsx` выбирает лендинг или приложение по адресу страницы.
2. `RealApp` ищет токен `mova-session`. В браузере он хранится в `sessionStorage`, то есть отдельно для каждой вкладки. В Electron токен хранится в `localStorage` и переживает перезапуск.
3. Если токен есть, клиент вызывает `/api/me`. При неверной или истёкшей сессии токен удаляется и показывается вход.
4. После входа `Product` сначала берёт списки и выбранный чат из cache в памяти текущей страницы, если cache уже существует.
5. Затем клиент загружает `/api/conversations` и `/api/users` при отсутствии свежего cache и подключает `/ws`.
6. WebSocket получает событие `ready`; heartbeat клиента и ping/pong сервера контролируют «зависшее» соединение.

После полной перезагрузки страницы cache чатов и сообщений пустой: это обычные JavaScript `Map`, а не постоянное локальное хранилище.

### Что происходит при открытии чата

1. Выбранный `conversationId` сохраняется в `localStorage`.
2. Клиент ищет историю этого чата в `messageCache`.
3. Свежий cache моложе 60 секунд показывается без нового запроса.
4. Устаревший cache показывается сразу, но параллельно заменяется ответом `/api/conversations/:id/messages`.
5. Сервер возвращает последние 200 сообщений из SQLite в хронологическом порядке.
6. Видимые входящие сообщения отмечаются прочитанными через `/read`, а сервер рассылает `message:read` другим участникам.

Сейчас нельзя запросить 201-е и более старые сообщения. Поиск в чате тоже работает только по уже загруженным максимум 200 сообщениям.

### Что происходит при отправке сообщения

1. Composer сразу очищается.
2. Клиент создаёт временное сообщение с локальным `clientId`, показывает его в истории и поднимает чат наверх списка.
3. Пока сервер не ответил, виден статус `sending` с часами.
4. Если есть вложение, изображение заранее обрабатывается на устройстве. Во время отправки файл сначала отдельным бинарным запросом загружается в `/api/uploads`.
5. Затем POST `/api/conversations/:id/messages` отправляет текст, ссылку на загрузку, ответ на сообщение и `clientId`.
6. Сервер проверяет участие в чате, записывает сообщение в SQLite, привязывает загрузку к нему и рассылает `message:new` всем подключённым участникам, включая другие вкладки отправителя.
7. Клиент связывает подтверждение с временным сообщением по `clientId`, заменяет его серверным и показывает `sent`. После receipt другого участника появляется `read`.
8. При ошибке временный пузырь остаётся со статусом `failed`, но кнопки повторной отправки нет.

Важная деталь: `clientId` сейчас присутствует только в объекте текущего HTTP/WS-ответа. В таблице `messages` для него нет колонки. После чтения сообщения из SQLite `clientId` теряется, а повтор того же POST создаёт новое серверное сообщение.

### Где хранятся данные

- Пользователи, чаты, участники, сообщения, read-state и метаданные загрузок: SQLite `.mova-data/db.sqlite` локально или `/data/db.sqlite` на Amvera.
- SQLite включён в WAL-режиме, использует foreign keys, busy timeout, индексы и транзакции.
- Сами файлы: `.mova-data/uploads` локально или `/data/uploads` в production.
- В SQLite хранится описание вложения и его URL, но не тяжёлый base64.
- Старый `db.json` импортируется безопасно и остаётся резервной копией.
- Выбор чата, настройки, локальные mute/block и часть настроек звонка: browser storage.
- Cache истории: только память вкладки/renderer-процесса.

### Как другой пользователь получает сообщение

После успешной записи в SQLite сервер вызывает broadcast `message:new` для участников чата. Открытый клиент добавляет сообщение в cache нужного чата, обновляет preview и список чатов. Если окно не в фокусе, создаётся Web Notification и проигрывается звук.

WebSocket ускоряет доставку, но SQLite остаётся фактическим источником истины. Проблема в том, что клиент пока не всегда перечитывает эту истину после пропущенного WebSocket-события.

### Что происходит при отключении WebSocket

- Клиент замечает close или heartbeat timeout.
- Повторное подключение выполняется с задержкой примерно от 0,5 до 8 секунд.
- События `online` и возвращение вкладки в видимое состояние ускоряют попытку reconnect.
- До 200 исходящих WebSocket-команд временно складываются в память и отправляются после reconnect.
- Сервер отдельно проверяет сокеты ping/pong и отключает слишком медленных клиентов.
- При повторном `ready` клиент перечитывает список чатов и пользователей.
- Открытая история сообщений при этом не перечитывается и общего event cursor нет.

Следствие: сообщение, пришедшее во время разрыва, будет видно как preview в списке чатов после sync, но может отсутствовать внутри уже открытого чата до переключения чата или перезагрузки.

### Как работают звонки

- WebSocket используется для приглашения, состояния звонка и обмена WebRTC offer/answer/ICE.
- Аудио, видео и демонстрация экрана идут напрямую между клиентами WebRTC, а не через HTTP-сервер Mova.
- Для нескольких участников используется peer-to-peer mesh: каждый участник создаёт соединение с каждым.
- Сервер хранит активные звонки и комнаты в памяти процесса. Перезапуск сервера завершит этот контекст.
- Клиент получает STUN/TURN-конфигурацию из `/api/rtc-config`. Код поддерживает TURN через runtime secrets; без них остаются публичные STUN-серверы.
- После сбоя peer connection выполняется ICE restart. После reconnect WebSocket клиент синхронизирует звонок, повторно входит в voice room и заново договаривается с peers.
- Каждые 3 секунды собираются RTT, jitter, packet loss, тип ICE-кандидатов, протокол и объёмы аудиобайтов. UI показывает полосы качества и задержку.
- Если пользователь говорит, а исходящие аудиобайты несколько проверок не растут, клиент пытается восстановить ICE.

Пока не собираются фактический bitrate за интервал, FPS, dropped frames и показатели нагрузки encoder/decoder. Диагностика не сохраняется и не может быть приложена к обращению пользователя.

### Как устроен Electron-клиент

Electron не содержит отдельную копию backend/frontend. Production-оболочка просит HTTPS-адрес Mova и открывает с него `/app` в `BrowserWindow`.

Полезные desktop-возможности уже есть:

- одно окно приложения и single-instance lock;
- постоянная desktop-сессия;
- разрешения микрофона, камеры, уведомлений и screen capture только для настроенного origin;
- системный выбор окна/экрана;
- запрет навигации на недоверенный origin, внешние ссылки открываются системным браузером;
- sandbox, отключённый Node.js в renderer и context isolation;
- автообновление через GitHub Releases с установкой после подтверждения.

### Отличия desktop от веб-версии

| Веб | Electron |
| --- | --- |
| Сессия изолирована на вкладку и не переживает закрытие вкладки. | Сессия хранится постоянно для desktop user profile. |
| Разрешения и screen picker контролирует браузер. | Разрешения ограничены настроенным origin, screen picker запускает Electron/ОС. |
| Нет автообновления приложения. | Оболочка проверяет GitHub Releases и скачивает update. |
| Обычная browser-навигация. | Внешние origin блокируются в окне и открываются снаружи. |
| Работает, пока открыта вкладка. | Работает как отдельное single-instance приложение. |

При этом сообщения, cache, offline-очередь и WebRTC находятся в общем React-коде. Electron main process не дублирует бизнес-логику, что является правильным разделением.

## 2. Что уже сделано хорошо

1. **Optimistic UI уже есть.** Сообщение появляется сразу, имеет `sending/failed`, а подтверждение примиряется по `clientId`. Это нужно укрепить, а не переписывать.
2. **SQLite используется осмысленно.** WAL, foreign keys, индексы, транзакции и обратимо организованный импорт JSON — хорошая база для безопасной эволюции.
3. **Вложения вынесены из базы.** Есть бинарная загрузка, проверка размера/формата, ownership незавершённой загрузки и очистка orphan-файлов.
4. **Изображения обрабатываются на клиенте.** Маленькие файлы сохраняются без потерь, крупные уменьшаются, а WebP берётся только при заметной экономии.
5. **Realtime не оставлен без контроля соединения.** Есть heartbeat, server ping/pong, reconnect с backoff, wake по online/visibility и защита от медленного socket-клиента.
6. **Read receipts хранятся компактно.** В membership хранится последняя прочитанная позиция, а UI различает sent, частично прочитано и прочитано всеми.
7. **Звонки уже умеют восстанавливаться.** Есть perfect-negotiation-подобная защита от конфликтующих offer, очередь ICE candidates, ICE restart, возврат в активный звонок и runtime TURN-конфигурация.
8. **WebRTC stats реально используются.** RTT, jitter, loss и candidate pair влияют на индикатор качества; застой исходящего аудио вызывает recovery.
9. **Electron ограничивает доверие.** Renderer sandboxed, Node integration отключён, разрешения и навигация привязаны к одному origin.
10. **Есть полезные автоматические проверки.** На момент аудита прошли 12 test files / 62 теста и серверная integration-проверка миграции, сообщений, файлов, receipts, realtime, TURN config и восстановления звонка.

Эти механизмы следует развивать в существующих `api.ts`, `RealApp.tsx`, `useVoiceCall.ts`, `server/index.mjs` и `database.mjs`, а не создавать параллельный messenger core.

## 3. Что мешает Mova ощущаться как Telegram

### Самое опасное место

Самый опасный сценарий — «сервер сохранил сообщение, но клиент не получил подтверждение». Клиент покажет `failed`. Пользователь естественно попробует отправить ещё раз, а сервер создаст вторую запись, потому что `clientId` не сохраняется и не имеет уникального ограничения. Если же приложение закрыть до повтора, failed-сообщение исчезнет из памяти. Это одновременно риск дублей и риск того, что пользователь не понимает, сохранилось сообщение или нет.

### Остальные критичные разрывы

- **Reconnect не закрывает пропуск истории.** Обновляется overview, но не открытый чат; нет server event/message cursor.
- **История ограничена 200 сообщениями.** Нет `before/after`, пагинации и сохранения позиции scroll.
- **Cache не переживает reload.** Быстрый повторный вход работает только в рамках текущей загруженной страницы и 60-секундного cache.
- **Offline отправка отсутствует.** Нет постоянного outbox, автоматического retry и понятного состояния «ожидает сеть».
- **Черновики отсутствуют.** Текст, reply и вложение сбрасываются при переходе в другой чат.
- **Загрузка непрозрачна.** Пользователь не видит progress, не может отменить или повторить только upload; data URL временно удваивает расход памяти на больших файлах.
- **TURN поддержан кодом, но факт production-доступности не доказан репозиторием.** Нужен runtime-тест relay candidate через мобильную сеть/сложный NAT.
- **Диагностика звонков неполная.** Нет interval bitrate, FPS, dropped frames, encoder/decoder metrics, истории и экспортируемого отчёта.
- **Mute уведомлений содержит функциональный разрыв.** `mova-muted-<chat>` меняет UI-настройку, но обработчик входящего `message:new` не проверяет её и всё равно показывает notification/звук.
- **Некоторые UI-действия только локальные.** «Удалить чат» убирает чат из React-state без server API, поэтому он вернётся после reload. «Заблокировать» также является локальным флагом, а не серверным правилом.
- **Два крупных файла концентрируют слишком много обязанностей.** `src/RealApp.tsx` превышает 3 000 строк, `server/index.mjs` — 900. Это не повод для rewrite, но каждую следующую серьёзную функцию нужно постепенно выделять в модули.

## 5. Дорожная карта маленькими этапами

### Этап 1 — идемпотентная отправка и безопасное «Повторить»

Цель: один пользовательский send должен создавать не более одного серверного сообщения, даже если HTTP-ответ потерян и запрос повторён.

- Безопасно добавить `client_id` в SQLite и уникальность по автору + `client_id`.
- Сохранять/возвращать `clientId` после повторного чтения из базы.
- При повторном POST с тем же `clientId` возвращать существующее сообщение и не делать повторный broadcast.
- Дать failed bubble действие «Повторить», повторяющее тот же payload с тем же `clientId`.
- Добавить integration test: два одинаковых POST → одна строка и одно realtime-событие.

Файлы: `server/database.mjs`, `server/index.mjs`, `src/lib/api.ts`, `src/RealApp.tsx`, `src/RealApp.test.tsx`, `server/integration.mjs`.

Почему первым: без server idempotency любой auto-retry/offline outbox способен сам создавать дубли.

Ручная проверка: открыть один чат в двух окнах, отправить сообщение, оборвать сеть до получения подтверждения, вернуть сеть и нажать «Повторить». В обоих окнах должен остаться ровно один пузырь, после reload — тоже один, со статусом «Отправлено».

### Этап 2 — обязательная сверка после reconnect

Цель: сообщения, пришедшие во время разрыва WebSocket, всегда появляются без ручной перезагрузки.

- На повторном `ready` синхронизировать открытый чат, а не только overview.
- Примирять ответ с optimistic/failed items, не затирая локальное состояние вслепую.
- Добавить тест сценария «socket отключён → сообщение сохранено → reconnect → открытая история догнана».
- На первом маленьком шаге допустима сверка последних сообщений; затем её заменит cursor из этапа 3.

Файлы: `src/lib/api.ts`, `src/RealApp.tsx`, `server/integration.mjs`, UI/integration tests.

### Этап 3 — cursor и пагинация истории

Цель: получить всю историю, не загружая её целиком.

- API `limit` + стабильный `before` cursor для старых сообщений.
- При необходимости `after`/sync cursor для точного восстановления пропусков.
- Загрузка следующей страницы при прокрутке вверх с сохранением положения экрана.
- Проверки одинакового timestamp, отсутствия пропусков и дублей между страницами.

Файлы: `server/database.mjs`, `server/index.mjs`, `src/lib/api.ts`, `src/RealApp.tsx`, tests.

### Этап 4 — постоянный outbox и offline sending

Цель: сообщение не теряется при reload и само/по команде отправляется после возвращения сети.

- Небольшой IndexedDB outbox с версией схемы; не переносить в него весь продукт сразу.
- Состояния `queued`, `sending`, `sent`, `failed`; стабильный `clientId`.
- Ограниченный backoff и ручное управление retry, без бесконечного спама серверу.
- Очистка outbox только после server ack.

Файлы: новый `src/lib/messageOutbox.ts`, `src/lib/api.ts`, `src/RealApp.tsx`, tests.

### Этап 5 — постоянный cache истории и черновики

Цель: посещённый чат открывается сразу после перезапуска, а незаконченный текст не пропадает.

- Версионированный IndexedDB cache страниц истории с лимитом размера/LRU.
- Сначала показать cache, затем тихо синхронизировать по cursor.
- Хранить черновик по `userId + conversationId`: текст, reply; вложение — только если выбран безопасный способ хранения Blob и лимиты.
- Очистить draft после подтверждённой постановки сообщения в outbox.

Файлы: новые `src/lib/messageCache.ts`, `src/lib/drafts.ts`, `src/RealApp.tsx`, tests.

### Этап 6 — надёжные загрузки файлов

Цель: progress, cancel и retry upload без повторной отправки текста.

- Upload transport с progress и AbortController/XHR там, где `fetch` не даёт progress.
- Отдельные состояния подготовки, загрузки и отправки сообщения.
- Повторно использовать уже загруженный URL после сетевой ошибки.
- Решить и задокументировать политику авторизации скачивания вложений.

Файлы: `src/lib/api.ts` или новый upload module, `src/RealApp.tsx`, `server/index.mjs`, `server/database.mjs`, tests.

### Этап 7 — корректные unread и уведомления

Цель: mute действительно выключает уведомления, а пользователь понимает, где есть непрочитанное.

- Применять mute до звука/notification.
- Вернуть unread count/последнюю прочитанную позицию в overview.
- Добавить badge в список чатов и desktop dock/taskbar при обоснованной необходимости.

Файлы: `server/database.mjs`, `server/index.mjs`, `src/RealApp.tsx`, `src/lib/messageNotifications.ts`, позже `desktop/main.mjs`.

### Этап 8 — production-проверка TURN и отчёт звонка

Цель: различать проблему устройства, прямого маршрута и TURN.

- Smoke test, который требует relay candidate и проверяет UDP/TCP/TLS endpoints.
- Добавить interval bitrate, codec, FPS, frames dropped/encoded/decoded и freeze metrics.
- Локальный диагностический отчёт «скопировать данные звонка» без чувствительных IP/секретов.
- Не отправлять телеметрию на сервер без отдельного продуктового решения.

Файлы: `src/hooks/useVoiceCall.ts`, `src/RealApp.tsx`, call tests, deployment/README.

### Этап 9 — расширенные сценарии восстановления звонка

Цель: проверяемый recovery при смене Wi‑Fi/мобильной сети, sleep/wake и временном падении signaling.

- E2E-сценарии disconnect/reconnect media и signaling.
- Понятные состояния «восстанавливаем», timeout и ручное переподключение.
- Проверить предел mesh-звонка; не менять топологию без измерений и продуктовой потребности.

Файлы: `src/hooks/useVoiceCall.ts`, `server/index.mjs`, `server/call-e2e.mjs`.

### Этап 10 — desktop-надежность и обновления

Цель: диагностируемый update flow и только полезные нативные возможности.

- Периодическая проверка update и понятный статус ошибки/версии.
- Проверка подписанных macOS/Windows release artifacts на тестовом релизе.
- Отдельно оценить tray, badge и deep links; не переносить сообщения в Electron main.

Файлы: `desktop/main.mjs`, `package.json`, release workflow, при опубликованной версии `src/LandingPage.tsx`.

### Этап 11 — убрать ложные UI-действия и постепенно разделить большие файлы

Цель: интерфейс не обещает то, чего сервер не делает, а новые изменения остаются проверяемыми.

- Либо реализовать server semantics delete/block, либо временно не показывать действия как завершённые.
- По мере работ выделять message store/outbox/cache/composer из `RealApp.tsx`, routes и realtime handlers из `server/index.mjs`.
- Не делать самостоятельный rewrite и не менять стек.

## Первые пять этапов одним списком

1. Идемпотентная отправка + безопасное «Повторить».
2. Сверка открытой истории после WebSocket reconnect.
3. Cursor и пагинация старых/новых сообщений.
4. Постоянный outbox и offline sending.
5. Постоянный cache истории и drafts.

## Рекомендация владельцу продукта

Начать с этапа 1. Он маленький по продуктовой поверхности, не требует rewrite и закрывает самый неприятный класс ошибок: «непонятно, отправилось ли сообщение» и дубли после повтора. После него можно безопасно автоматизировать retry и offline-доставку.

После реализации этапа 1 вручную проверить:

1. Обычная быстрая отправка по-прежнему показывает сообщение сразу.
2. Сначала видны часы, после ack — галочка.
3. При отключённой сети пузырь становится failed и не исчезает.
4. После включения сети «Повторить» меняет тот же пузырь, а не создаёт новый.
5. У второго пользователя приходит ровно одно сообщение и одно уведомление.
6. После reload у обоих пользователей в истории всё ещё ровно одна копия.
7. Обычная отправка текста, ответа и вложения продолжает работать.
